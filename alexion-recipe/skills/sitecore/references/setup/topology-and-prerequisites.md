# Topology and prerequisites

Before any remote operation, record source and target independently: connector alias, platform, version/build, site name/root, database, language, role and supported capabilities. The aliases may address one XP installation for xpmvc2xpheadless; retain distinct read/write roles nevertheless.

For the **source** connector, classify topology/role/HS-install state deterministically instead of guessing from repository config: run [`probe-topology.ps1`](../../scripts/setup/probe-topology.ps1) (no parameters, single ~1-2s round trip) through `run-powershell-script`, then [`classify-topology.mjs`](../../scripts/setup/classify-topology.mjs) on its JSON result. This returns topology (XP/XM, with a confidence tier and a `mismatch` flag when license shape and deployment shape disagree — e.g. an XP-licensed instance with an XM deployment), role (CM/CD/Standalone/Processing/Reporting/XMCloud), and a preliminary Headless Services install signal consumed by [headless-services-install.md](headless-services-install.md). It is preliminary evidence, not Layout Service readiness: DLL/config-file anchors must never be classified as a missing or misconfigured Layout Service. Final Layout Service readiness requires a selected site and a connector-owned authenticated Layout Service probe. **Sitecore 9.0+ sources only**: role detection degrades gracefully on older kernels (falls back to file-presence markers), but topology classification does not — its deployment-side signals are xConnect artifacts that don't exist before 9.0, so a genuine pre-9.0 XP source can be confidently misclassified as XM, not just flagged low-confidence. Do not run this pair against, or trust its topology verdict for, a pre-9.0 source.

Use the canonical script as the behavioral source. Whitespace or line-ending differences introduced while forwarding the script are not a capability failure when the remote result is terminal and the raw output schema validates. Only a wrapper or transformation that changes execution or output shape requires a bounded corrective retry.

Unknown version or missing permission is an evidence gap, not permission to install the latest package. Probe only the capability needed beyond topology: source items/SPE, Layout Service, GraphQL or target management/serialization.

For MVC discovery-only work, missing Headless Services need not block code inspection. It does block claims of a resolver-expanded layout baseline. Record that limitation. For XP Headless verify compatible JSS/Headless Services; for XMC verify target Edge and management capabilities separately.

Run the independent focused procedures in `../../scripts/setup/README.md`, normalize their verdicts, and apply [the capability requirements](capability-requirements.md) with `../../scripts/setup/evaluate-prerequisites.mjs`. Save its result with observed version, probe/evidence references, remediation owner and next action as `reports/setup-prerequisites.json` so later tasks and chats read it instead of re-deriving it. Delegate authentication to connectors, installation to [Headless Services](headless-services-install.md), patch assessment to [hotfixes](hotfixes.md), and API-key handling to [API keys](api-key.md). Never include secret values in reports or scripts.
