# Configure the assigned Sitecore role

Use during `setup.source` or `setup.target` after loading the migration-artifact role template and [role completion contract](../../../migration-artifact/references/role-setup-contract.md). Work only on the assigned role; do not enter Discovery or run the complete cross-role CMS pipeline.

## Connector and site identity

Validate the connector selected by this role’s migration-artifact selection step using the required bounded read-only access/health checks. Reuse confirmed connector access and terminal checks. Troubleshoot a failed required check using its documented connector procedure; do not invent endpoints, aggregate probe scripts or repeat successful work. Use [topology](topology-and-prerequisites.md) for unresolved product/version facts and [site enumeration](site-enumeration.md) for unresolved XP/XM site choices. On SitecoreAI/XM Cloud targets use the active connector's `xmc-list-sites` and, when needed, `xmc-list-collections`, preserving terminal results. Do not use an XP configuration-Factory probe against XM Cloud or guess a site from `xmcloud.build.json`.

Reuse an explicit applicable site choice; otherwise present the actual candidates and ask the user to confirm the source or target site. Never auto-select even one result or infer a target site from a matching source name, repository or rendering-host app. An existing same-name target site is a candidate, not migration authorization. Verify the selected site/root with the assigned connector and resolve the applicable language(s) with the user using actual availability. Source scope and target destination are separate choices. Do not duplicate an already confirmed role answer.

Record supported verified values in the assigned role file’s `artifactRole` object and in the assigned migration artifact role before role completion: `site.name`, `site.rootPath`, `site.startItem`, `site.hostName`, platform/product and `version`, rendering architecture and SDK type/version under `rendering`, selected repositories/`branchName`/`sandboxDir`, SXA facts, and credential-free HTTP(S) supporting references (`type: "url"`, `description`, `url`). Rendering architecture is `mvc` or `headless`; SDK type is `jss` or `content-sdk`; omit sdk if neither applies or it is unknown. Keep verified capability/health findings in task-owned evidence and sandbox execution state, never in the artifact role. Populate all applicable facts already known; an allowed optional field is not permission to omit a verified fact. Leave genuinely unknown or inapplicable fields absent and explain them in role evidence. Languages and other execution-only values belong in the role handoff and coordinator-owned context/decisions when not exposed by the artifact schema.

If the destination site does not exist, resolve the intended destination and explicit create/adopt/defer choice with the user. Keep planned versus verified-existing values distinct in evidence; do not claim a created site or fabricate its path/host. A required unresolved target identity blocks role setup. Actual provisioning, overwrite and publish need their scoped authorization and applicable CMS initialization gate; a documented later creation does not waive that gate.

## Repository and tech stack

Follow the role template's acquisition and credential rules. Inspect only the selected checkout/app's authoritative manifests and relevant configuration to establish platform version, MVC/headless rendering architecture, framework, SDK type/version, app name and app root. Distinguish a declared dependency range from a resolved installed version; record the available fact accurately and the limitation in evidence. Use supported artifact fields; tech-stack facts without schema fields still belong in `role-configuration.json` for coordinator state/evidence.

Inspect rendering-host configuration using allowlisted non-secret fields only; never print the entire `xmcloud.build.json`, `jssDeploymentSecret`, environment values or credentials. An app name is not a Sitecore site identity. For source Headless Services/Layout checks, select site/language before a selected-site probe and follow [capability requirements](capability-requirements.md). Save reusable terminal evidence and leave migration-type/mode applicability to the CMS evaluator when those cross-role choices are not yet known.

Follow the isolated role persistence and owner completion contract. Read back the task-owned role file, save/read back the final Technical report and set done when this role meets its criteria. Save and read back the assigned artifact role with the latest complete content, preserving the opposite role. Source completes before target starts. Do not write combined sandbox context/decisions. The CMS setup owner verifies the saved artifact roles and builds combined context; missing known selected site or SDK facts block integration. Sitecore mutation, package installation, repository initialization, commits and pushes are not authorized by configuration inspection.

For downstream role-file inspection, follow the `cms-migration` skill's `references/context-file.md#inspect-json-evidence-before-composing-helpers`, resolved from that skill's root. Preserve the role/probe producer's actual field types; its `checks` may be a keyed object rather than the evidence contract's array. Consumers inspect the shape before indexing or mapping and validate the separate TASK_RESULT before reading its required fields. A local helper error does not invalidate successful remote checks or authorize rewriting the role evidence.


## Artifact-to-context field mapping

Map Sitecore artifact `source.site.rootPath` to context `source.site.path`, with confirmed languages/primaryLanguage from role evidence; target site identity stays in artifact `target.site` and evidence because context has no target.site field.
