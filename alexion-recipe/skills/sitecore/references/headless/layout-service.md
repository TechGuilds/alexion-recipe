# Layout Service capture and interpretation

The source Layout Service response is the evidence for resolver-expanded rendering fields, route context and ordered placeholder composition. Generic item GraphQL is not an equivalent substitute.

Resolve source connector, site name, route, language, database/version and editing mode explicitly. The native [export-layouts.ps1 contract](../../scripts/capture/README.md) calls the actual /sitecore/api/layout/render/jss REST endpoint with item/sc_site/sc_lang and a server-resolved sc_apikey. APIKeyItemPath is a source item path beneath /sitecore/system/Settings/Services/API Keys; the GUID key value remains on the source server, never in connector parameters, saved scripts or artifacts.

ApprovedOrigin must match the connector-reserved $KajooSourceOrigin injected from powershellServerUrl.origin. The connector rejects user-parameter collisions; callers must not supply this variable. Missing/mismatched injection fails closed. HttpContext is not required or consulted, so asynchronous SPE sessions are supported irrespective of background selection. HTTPS is required except same-source loopback HTTP; redirects and alternate origins remain rejected. The supported mode is delivery, latest, site-default device, with the site's configured database matching the explicit Database. Custom devices, numbered versions, preview and editing are unsupported. No browser cookies or inherited credentials are forwarded.

Raw response bytes stream into unique files under source Data with per-route statuses, hashes and a partial/completion summary using the shared kajoo-export helper. Download through the source connector into writable evidence; never write inside installed skills. Request metadata excludes the key/query, and exception/HTML/error snippets are not returned. A partial capture or failed transfer is not a complete baseline.

Check sitecore.route, context, rendering fields, placeholder children and error payloads. A successful transport with a null route is a failed capture. Record redirects, unknown routes, unsupported modes and pagination of any surrounding route inventory. Delivery and editing captures remain separate.

Keep the original response immutable. normalize-baseline.mjs implements only explicit raw-file to output-path mappings and requires a complete capture by default; optional Discovery samples may explicitly use `--allow-partial` to deliver every verified successful route while retaining failed-route records and partial coverage in the derived manifest. It copies bytes unchanged to an exclusive new output directory. It does not infer URL replacements or rename component/site fields. Field wrappers, component names, UIDs, datasource, parameters, large numeric values and occurrence ordering remain exact. The derived manifest records source paths/hashes, output hashes and mapping/capture-metadata hashes. Any future content transformations need a separate explicit mapping and validation contract.

The focused PowerShell container test runs real HttpClient requests against a mock HTTP server, with Sitecore API test doubles. It does not establish real Sitecore resolver execution, authentication/licensing behavior or source runtime compatibility. Those require validation on the selected source instance.

Capture MaxResponseBytes and normalization --max-bytes are optional per-file guards with configurable defaults, accepting higher positive safe integers. There is no task-wide maxTotalBytes dependency or fixed 128/256 MiB ceiling. Validation buffers one file at a time, including JSON/string overhead; choose limits appropriate for available memory and runtime buffer/string capacity.

For XMC, inspect the target Edge schema through the target connector, then request its layout using its own site/route/language. Compare only equivalent contexts. XP Headless targets continue using their verified Layout Service endpoint. See [baseline capture](../discovery/baseline-capture.md).
