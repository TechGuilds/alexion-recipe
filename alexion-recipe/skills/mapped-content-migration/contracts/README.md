# Mapped Content Migration contracts â€” version 1

These contracts describe mapping-based content migration inputs and outputs. Read the [skill](../SKILL.md), [execution runbook](../references/execution.md), [source preparation](../references/source-snapshot.md), [recovery rules](../references/recovery.md) and [script inventory](../scripts/README.md) for responsibilities, evidence and available operations. Local validation/preparation does not execute target migration or activate workflow tasks. Source requests require separate approval and connector submission.

`sitecore-mapping.ts` defines template/field, rendering and placeholder mappings. `sitecore-mapping.schema.json` validates its JSON representation. The raw mapping has no version property; the input manifest supplies `version` and `mappingRevision`. IDs identify items and fields; names and paths are checked against target evidence to detect inconsistent input. A mapping warning is descriptive evidence, never an executable rule or approval.

`definitions.schema.json` is the runtime authority for the version-1 documents. The named schema files expose each document to JSON Schema 2020-12 validators; register `definitions.schema.json` by its `$id` before loading them. `migration-contracts.ts` documents the companion shapes for producers. TypeScript types do not replace runtime validation. Keep connector credentials outside these documents; the validator is not a credential scanner.

The [input reference](../references/input-contracts.md) describes supported semantics and validation limits. Files under `tests/fixtures/` are synthetic examples, not discovery evidence or approved migration inputs. Their field types, paths and values are illustrative and must not determine real migration decisions.

The [local transformer](../references/transformation.md) consumes `transform-input.schema.json`, binding a migration manifest and snapshot-validation request. It requires a complete prepared source manifest. Generated item plans additionally record optional `versions`, `parentPath` and `structures` (explicit folder definitions). Older plans remain structurally compatible. Proposed identity maps are planning evidence; they do not record successful writes. Branch expansion is blocked; see [operational boundaries](../references/operational-boundaries.md#supported-and-excluded-work).

The [dry-run planner](../references/dry-run.md) consumes `plan-input.schema.json` and verified observations conforming to `target-state.schema.json`. It emits a review-only `batch-plan.schema.json` artifact with all-output drift preconditions and bounded operations. The transformation report now binds its plan and identity-map bytes by hash; older reports require local regeneration. These contracts do not authorize writes or establish freshness automatically.

The [reference planner](../references/reference-resolution.md) consumes [reference-plan-input.schema.json](reference-plan-input.schema.json), binding the original content planner input, an immutable identity checkpoint and fresh target observations. Optional `destinationPlan.existingReferenceTargets` entries select exact inventoried target content/media items for read-only reuse; optional `existingTargetState` supplies their current ID/path/template observations under the read-only `/sitecore` root. Missing or conflicting evidence withholds all batches. Execution uses `operationKind: references` with the existing execution input/review, writer, approval and journal contracts. References create no items or versions. Reference receipts preserve initial-content identity provenance; they do not authorize dependent work from partial or failed identities. The unchanged raw mapping files remain the template/rendering/placeholder mapping format.

Capture header/completion schemas enforce the supported response version and effective-value semantics. Optional source `fieldType`, destination `fieldCompatibility` decisions and [ownership rules](../references/ownership.md) make type/ownership requirements explicit. The original supplied mapping interfaces remain unchanged. Older untyped evidence needs reviewed type compatibility rather than assumed correctness; newly captured values carry actual source types.

Target execution uses [execution input](execution-input.schema.json), [verified capabilities](execution-capabilities.schema.json), [journal scope](execution-scope.schema.json), [immutable checkpoints](execution-checkpoint.schema.json), the existing CMS [mutation decision shape](execution-decision.schema.json), [terminal receipts](execution-receipt.schema.json) and [journal events](execution-event.schema.json). The [execution review](execution-review.schema.json) binds exact target scope, operation postconditions, current guards, capabilities, writer hash and input/checkpoint hashes before approval and reservation. Template evidence contains complete transitive `baseTemplateIds` and all effective fields, including inherited field IDs, declaring template IDs, names, types and sharing modes. Execution must verify both the transitive base identities and effective field metadata against that evidence; unchanged field counts alone do not establish unchanged inheritance. Structural schema validation does not authenticate approval, prove a backup is restorable or establish live connector compatibility.
