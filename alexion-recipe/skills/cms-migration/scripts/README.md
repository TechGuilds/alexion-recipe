# CMS filesystem CLIs

Requires Node.js 20+, no install/SDK/connectors/database. All shared scripts accept `--input staged.json` and optional `--out new-report.json`. Staged documents are inline JSON objects; artifact paths resolve relative to the input file unless the script explicitly names a canonical workspace root. Destination flags resolve relative to cwd. Default is read-only; `--dry-run` explicitly selects the same behavior, optionally saving a new proposal/report. Stdout is a concise JSON summary; full output requires `--out`. Existing destinations (including symlinks) are refused; output parents must exist. Exit 1 means invalid input, evidence validation failure or filesystem error. Coverage gaps are report data, not process failures.

| Script | Inputs | Output and effects | Acceptance cases |
| --- | --- | --- | --- |
| build-work-items.mjs | inventory, profile, required approved current workflow, optional availableAgents | proposed one-task-per-entity workflow, mappings, warnings | duplicate IDs, parent cycles, hosting kept out of dependsOn, resume, orphaned tasks after re-discovery, missing agents |
| validate-context.mjs | the `context.json` document itself | `valid`, `complete`, `missingFields`, warnings; never writes | credentials, unsafe roots, missing fields per mode |
| extract-archive.mjs | archivePath, rootMarkers or rootPath, `--apply --destination NEW_DIR` | dry-run report, or the project root extracted into a new directory | zip-slip names, symlinks, `.git`, case collisions, lying sizes/CRC, root ambiguity |
| next-work.mjs | inventory, workflow, mappings, optional current inputs/validation/proceedWithoutHost, `--limit` | ranked reachable tasks (including user-approved batches), waiting items with reasons, status | seeds, any-of hosts, failed/skipped/out-of-scope hosts, grouped-task readiness, verification frontier, stale/missing attestations, override, ranking, limit |
| prepare-task-packet.mjs | canonical workflow/inventory/mappings, the selected task, target/attempt roots, declared evidence references and acceptance checks | one immutable, selected-task dispatch packet; never reads repositories or changes state | scope alignment, canonical next-task selection, mapped entities, stable input ordering, target/attempt path safety |
| validate-evidence.mjs | workflow, scopeId, inputs, result paths, decisions, optional required evidence kinds by task | verifiedTaskIds, current inputFingerprint, per-entity attestations and errors | stale hashes, missing files, malformed result, unapproved gates, missing required evidence kind |
| operation-providers.mjs | the profile registry `assets/profiles/<profile>/operation-providers.json` | library only: lists optional skills that supply canonical workflow operations and loads a provider module (`scripts/workflow-provider.mjs` in that skill) when a packet or evidence needs it. A missing provider skill fails with a clear message. |
| validate-task-attempt.mjs | task-owned path-only postflight request plus `--workspace-root` | one selected attempt's verification report | nested target roots, stale/unsafe task evidence, missing required evidence kind |
| coverage-report.mjs | inventory, workflow, mappings, decisions, optional validation/sampledRouteIds | counts and unmatched entity/route IDs | sampled scope, exclusions, missing tasks, duplicates |
| validate-workflow-plan.mjs | status-free proposal/evidence fingerprints, scope and decisions | validates the exact user-approved proposal without mutation | stale/empty/conflicting approval, malformed proposal, missing evidence |
| materialize-approved-workflow.mjs | approved proposal, active workflow and planning task ID | derives active statuses after approval without remote mutation | changed existing structure, non-terminal planning dependency, malformed input |
| validate-workflow-sync.mjs | approved proposal, active workflow, bindings and artifact phase IDs | verifies post-sync structural parity before dispatch | workflow-structure drift, missing/duplicate bindings, artifact epic mismatch |

See ../references/work-ordering.md for how `next-work.mjs` decides what is reachable and why hosting is not a dependency edge, and ../references/executable-contracts.md and ../assets/contracts/*-input.schema.json for exact envelopes. All shared scripts use these schemas at runtime. Ordinary state updates remain native coordinator edits.

`build-work-items.mjs` is for an explicitly approved item-level breakdown. For batches/milestones, the coordinator authors the approved task grouping and maps each included entity to the shared task ID; `next-work.mjs` waits until every member is reachable and recommends the task once. Run `node --test tests/cli.test.mjs` from the skill directory. Tests include real filesystem subprocesses and a self-contained copied skill.

For Content Migration, supply the existing approved scope decision as optional `contentMigrationDecision` to `prepare-task-packet.mjs`: its `choice` is `mapped-content` or `native-serialization`, scope/task and declared input hashes must match, and user response/timestamp must be recorded. The generator emits the selected mode and decision without editing shared state. Mode evidence does not grant mutation approval; missing mode blocks Content Migration dispatch. Other task kinds can omit it.

For a mapped implementation task, run `next-work.mjs` once, then run `prepare-task-packet.mjs` once for its selected `primary.taskId`. The packet contains only the selected task, its mapped entities, declared evidence references, target/attempt roots and acceptance checks. The coordinator must dispatch from that packet rather than re-reading global workflow state, schemas, skill source or unrelated reports. The active domain profile declares which retained evidence paths belong in `inputs`; absence or a hash/scope contradiction is a bounded blocker, not permission for broad rediscovery.

Coverage accepts optional current `inputs` (or `validation.inputs`); exclusions and explicit skips require matching nonempty fingerprints verified from actual files. Ordinary skipped status without a current entity/task decision stays unresolved. `validate-evidence.mjs` stages all referenced files under its input JSON's directory. For one worker attempt whose target repository is elsewhere, use `validate-task-attempt.mjs` once: its task-owned request names workspace-relative workflow, decisions, input and result paths and, when the task changes files, the target root relative to the explicit `--workspace-root`. It reads no paths outside that workspace and does not rewrite worker evidence. See executable-contracts.md for request shape, decision shapes and staging rules.
