# Discovery phase contract

Discovery establishes an evidence-backed source/target inventory and prepares a proposed plan for the phases that follow. This contract is platform-neutral; load the active migration profile for platform procedures, analyzers, output formats and phase examples.

## Entry and resume

1. Require Setup's terminal audit to be complete and an explicit user decision to enter Discovery. A new chat is not approval.
2. Read `context.json`, migration artifact, workflow, Kajoo plan bindings, current decisions and discovery manifests. Confirm the agreed migration type, source/target sides, code/content surfaces, exact connectors, source site/path, languages, route scope and relevant repository identity. Never infer a missing scope value from a default or from a connector name.
3. Present the Discovery work plan and ask for confirmation before starting remote reads. If resuming, verify each output against its manifest, scope and input fingerprint; reuse current successful outputs and rerun only missing, failed or stale branches. Rerun successful branches only when the user asks to restart or their inputs changed.

For remote reads, maintain an attempt-scoped `remote-runs.jsonl` beside the branch evidence. Before submission, record operation, scope, request fingerprint and status `prepared`; after submission record the returned run ID and `pending`; after the exact run terminates, record its terminal status, returned manifest/files and hashes. Check this ledger before every submission: never resubmit a matching request that is pending or terminal-successful. Resume/wait on the same run ID. Retry only after confirming the prior run is terminal-failed or the connector rejected the invocation before creating a run; preserve the prior row, record why, and bound the correction to one invocation-shape fix or one transient-failure retry. An unknown/lost result is not permission to resubmit. Distinguish `not-requested`, `not-attempted`, `pending`, `failed` and `unavailable` in the report; “unavailable” requires an actual capability attempt and evidence.

## Collect in parallel

Run independent requested code and content analyses in parallel. Each branch records its actual scope, provenance, full-versus-sampled coverage, counts, errors and output paths in an evidence file/manifest. Keep detailed payloads in files, not conversation context, migration memory or the Migration Artifact.

Separate independent static collection from dependent runtime example capture and delivery. When the user or active profile requests that delivery during Discovery, it must be attempted and reported, or explicitly deferred with scope, reason, evidence and an owner. Do not silently skip it as optional enrichment and claim it was delivered. Valid inventory collection can remain successful while that requested deliverable is incomplete. Follow the profile's current evidence and scope-approval procedure before execution; synthesis drafts alone grant no execution authority. Keep matching pending jobs on the same run ID and preserve the existing workflow-plan and phase-continuation gates.

Assess the assigned collection deliverables separately from completeness of every inferred relationship. An analyzer's exit 0 means it produced a report, not complete coverage; `complete: false` means inspect its omissions, not automatically fail the task. For a localized parser/tool limit, inspect the affected source with a bounded native/LSP read, retain the warning and any independently supported findings, and identify whether a required Discovery finding is still missing. Fail when required collection remains unavailable or unusable; keep optional enrichment and later implementation verification as explicit report limitations with an owner. Never claim full coverage from a partial report.

For `TASK_RESULT`, checks express the assigned stage's acceptance criteria (scoped collection, retained readable outputs, provenance and classified gaps), not unrequested runtime parity. A completed collection can return success with partial observations preserved in its referenced report; unresolved required acceptance failures remain in `unresolved` and prevent verified success. Classifying a gap does not satisfy an explicitly assigned required finding: that task remains unsuccessful until the finding is recovered or its scope is explicitly changed. Coordinator-owned planning uncertainties must be highlighted in the returned summary and report and resolved before audit can pass. Do not erase warnings, change failed checks to passed, or hide a required gap merely to satisfy `validate-evidence.mjs`. The coordinator assesses phase-changing gaps before audit separately from the worker's collection outcome.

- **Content is load-bearing for synthesis.** A content branch must return valid scoped evidence. Failed collection, empty results and a valid zero-result query are different outcomes. Content failure prevents synthesis and keeps Discovery blocked.
- **Code is enrichment for synthesis.** Wait until the requested code branch reaches a terminal result before synthesizing, but a terminal code-analysis failure does not itself prevent synthesis after valid content evidence exists. Record the exact missing outputs and limitation. Do not turn absent code into unused-rendering or completed-code evidence.
- A requested failed branch still prevents Discovery from being reported as fully covered. Offer a bounded retry/correction or an explicit user-approved scope reduction; do not create an executable downstream plan that assumes missing evidence. A scope reduction records a `scope` decision against the same evidence fingerprints, changes that branch task from `failed` to `skipped`, and records the exact downstream limitation. Never relabel a failed branch as done.
- If an invocation failed because of a recognizable argument-binding, schema, serialization or invocation-shape defect, preserve the error, correct only the invocation shape once, and retry the same bounded read. Do not retry a real source error blindly or loop.
- Surfaces outside agreed scope are explicitly skipped, not failed. Record the scope decision and existing evidence provenance where available.

The workflow's `optionalDependsOn` edge expresses the non-blocking code-enrichment relationship: synthesis waits for a terminal code result and may proceed after a failed code attempt. A required `dependsOn` edge remains a hard gate. A failed requested branch still leaves the phase incomplete until repaired or explicitly removed from scope.

## Synthesize and audit

After the requested branches are terminal and required content evidence is valid, join findings using stable source identifiers and explicit mappings. Produce the profile's normalized inventory, route/coverage view, unresolved joins, exclusions as suggestions (not approval), and a synthesis report referencing raw evidence. Preserve source baseline evidence and exact coverage limits. Never claim that samples establish whole-site coverage.

When the active profile provides a deterministic local synthesis builder, invoke it once from a minimal, declared input that names only the terminal branch evidence roots and verified scope. The builder may read only those declared inputs and write a fresh, attempt-scoped **draft** evidence directory. It must not enumerate the workspace, search repositories, call a connector, or change an active plan. A missing or contradictory declared input is a bounded evidence gap, not permission to reconstruct Discovery ad hoc. Any further remote or repository probe must be a separately authorized, narrowly stated follow-up that can materially change phase applicability or the proposed scope.

The phase auditor checks the selected scope against manifests, complete versus sampled coverage, identifiers/joins, empty-result explanations, serialization or platform prerequisites, route coverage and usable baseline evidence. Report included, excluded, unresolved and not-collected counts separately, along with the actual route plan, evidence paths, optional-enrichment gaps and all decisions still needed. The audit task is the final Discovery project task; there is no synthetic “approve/continue” task.

Before closing the audit, classify gaps by their effect: missing required collection, missing information that could change the proposed phases/scope/dependencies, optional enrichment, or validation deliberately assigned to later work. Only the first two require Discovery follow-up. Run bounded follow-up reads within the existing analysis/synthesis tasks, preserving valid outputs, and re-audit the affected findings. If access or scope prevents classification, present that specific unresolved decision to the user; do not silently omit the affected workstream or claim the whole plan is settled. Later implementation validation may remain an explicit task with an assumption and acceptance criteria. Optional enrichment failure does not turn valid required collection into a failed branch.

## Propose the next workflow

During synthesis, read the active profile's phase catalog as non-exhaustive examples, not as a fixed sequence or an allow-list. Derive workstreams from source/target differences, dependencies, unsupported features, integrations and validation needs, including phases absent from the catalog. Classify candidates with evidence as applicable, not applicable or unresolved. A signal can justify a scoped phase that first validates its implementation strategy; it need not prove the eventual implementation. Resolve gaps that change phase selection before passing the audit. Derive dependencies from actual prerequisites and shared resources; never inherit example ordering without evidence.

Before generating the task breakdown, ask the user for the desired granularity separately for each applicable workstream. Offer relevant choices (for example, one task per component/item, batches grouped by a functional boundary, or milestone-level tasks) and allow a custom grouping. Do not assume one task per inventory entity. Then prepare the complete draft—phases, tasks, stable IDs, dependencies, scope, assumptions and unresolved evidence—and request explicit approval.

When an active profile needs a machine-checkable execution scope for a proposed
workstream, materialize it **during Discovery planning**, before the final
proposal is displayed. The profile derives the projection from the draft and
matching Discovery evidence, verifies ownership and dependency ordering, and
retains the exact manifest, item list and input hashes beside the draft. This
is not task generation: it cannot add, rename, split, reorder or activate
workflow tasks. A non-ready projection means revise the draft or resolve its
evidence/decision gap before asking for approval. Once approved, later phases
reuse that hash-bound projection; they do not rediscover scope or reconstruct
the workflow from task titles.

Use the profile's migration work units and distinguish raw inventory counts from included migration units before asking about grouping. Supporting files and internal modules are dependencies of those units unless evidence warrants separate shared work. Keep the full proposal draft-only while collecting preferences or resolving material gaps.

Present important results as concise Markdown tables or structured bullets. Use status words alongside optional symbols (✅ verified, ⚠ partial/deferred, ❌ failed). The Discovery summary shows scope, canonical counts with units, coverage, limitations and evidence links. The workflow proposal shows every candidate's applicability/reason, then the complete included phases with their tasks, grouping, dependencies, assumptions and acceptance evidence. Explicitly list deferred checks and their owner/task. Ask for approval of that displayed complete plan; a tool's structural validation result does not prove factual completeness. Keep the audit task done and do not create future active tasks while the proposal awaits a conversational decision.

Keep the proposal in a sandbox report as approval evidence and record the user's `workflow-plan` approval decision against the current scope, proposal fingerprint and evidence fingerprints. A proposal contains only phases, task structure, dependencies, scope and acceptance evidence; it never contains runtime status. Validate that exact approval with `validate-workflow-plan.mjs`. Rejection or requested edits leave active workflow, Kajoo epics/tasks and artifact phase IDs unchanged. Only after approval, run `materialize-approved-workflow.mjs` once with the approved proposal, current active workflow and completed planning-task ID. Promote its returned workflow to active state, reconcile it with Kajoo epics/tasks, persist their read-back bindings, and synchronize the existing Migration Artifact `content.phases` database-ID list. Validate those synchronized representations with `validate-workflow-sync.mjs` against the approved proposal and active workflow; it compares structure, while the active workflow owns status. Do not mutate the proposal or use it as a second workflow state after promotion. Do not extend the artifact schema or put evidence, task status, approvals or raw tool results in it.

Plan approval is not permission to start execution. After the approved plan is synchronized, ask separately whether to start the named next phase now, pause, or continue in a new chat; record an explicit `phase-continuation` decision before dispatch. Do not leave a task in progress while waiting for either decision.

## Profile boundary

The CMS hub owns gates, resume logic, synthesis/approval sequencing, report shape and workflow synchronization. A CMS/platform or migration-type profile owns connector-specific probes, source formats, platform analyzers, output details, applicability criteria and golden phase examples. Put vendor paths, product flavors, platform languages and migration-pair rules only in that profile's references/assets. Do not add platform-specific logic to this contract or generic tools.
