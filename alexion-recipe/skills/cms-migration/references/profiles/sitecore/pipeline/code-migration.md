# Code Migration — Sitecore profile

This phase exists only when the post-Discovery, user-approved workflow includes code work. Do not assume it is phase 2 or that Content Migration follows it. The approved workflow and evidence-backed dependencies are authoritative. The coordinator routes bounded tasks to a fresh frontend-developer; tester is an independent verifier when the approved plan calls for it. Use `frontend-migration` plus the applicable Sitecore source/target pair skill.

Use [rendering preview flow](../../../../../sitecore/references/discovery/rendering-preview-flow.md)
for the existing source inventory, approved rendering/variant capture plan,
mapping and reviewed local preview delivery. Requested Discovery preview capture
and delivery are attempted in Discovery; this phase consumes their current
evidence or the user's explicit deferral and assigned recovery owner. Never
silently defer that deliverable here, recapture unplanned sitemap/homepage extras,
or treat a staged route as proof of implementation or human verification.

## Entry and state

1. Confirm Setup and Discovery audit are complete, the user entered this approved phase, and the selected source/target repositories, branches, migration mode, site/language, route scope and target init mode match current `context.json` and current Discovery evidence. Do not infer a branch, repository, site, language or scope from connector defaults.
2. Read the approved `workflow.json`, `inventory.json`, `mapping.json`, `decisions.json`, current reports and current task evidence before planning or retrying. The primary code units are the in-scope Sitecore rendering entities from Discovery—not React AST candidates. Join each rendering ID to source implementation files and routes using evidence; preserve ambiguous/unmatched joins as gaps. Internal React modules are supporting dependencies, not new Sitecore rendering tasks by default.
3. Workflow task status is the sole current task-status authority. Inventory is stable source identity/scope/parent/route facts; mappings bind each entity to its approved workflow task; decisions record explicit scope, redo, skip, restore and verification choices; evidence is stored per attempt under `evidence/<task-id>/<attempt>/`. Follow each entity ID through the synthesis report and linked Discovery evidence to its Sitecore rendering definition, source implementation path(s), routes and data/resolver facts; the generic inventory intentionally does not duplicate those vendor-specific details. Do not dispatch implementation when a required join is missing or ambiguous—recover it from the retained evidence or record the gap. For a grouped task, each rendering needs its own structured `entity-result` JSON artifact (see `entity-result.schema.json`) bound to its stable `entityId`; it records outcome, checks, worker decisions, changed files, checkpoint and unresolved hazards. Supporting logs/screenshots remain separate evidence and cannot independently prove one rendering. Passing entity results can preserve verified items if another item in the batch fails. Do not create an untracked `component.*` journal or copy current task status into another file. Keep detailed logs/screenshots and checkpoint references in evidence, with concise summaries in task results/reports.
4. On resume, inspect the selected task result, all entity-bound evidence, current hashes and actual target files first. Reuse only current verified evidence. Repair a correctable tool invocation/input problem and retry safely; distinguish it from a source/target-system failure. Never launch duplicate work or report a previous success after its inputs/code changed.

## Prerequisites

- Reconcile the target repository and any existing bootstrap against approved context and Discovery; preserve unrelated work. Reuse code only when current evidence proves it satisfies this migration's requirements.
- Include one mandatory `preview-foundation` readiness task for new and adopted apps whenever the approved Code Migration scope contains rendering work. Assign frontend-developer and make all render-dependent tasks depend on its successful evidence. Follow [preview readiness](preview-readiness.md), including launch preparation, startup and agreed-route verification. A missing task is a plan gap: reconcile it through the existing workflow approval/sync procedure before rendering work. Reuse current Discovery delivery and plan only remaining prerequisite gaps. When the confirmed SitecoreAI / XM Cloud Content SDK target needs disconnected integration, use the existing [Sitecore Headless-to-XMC mock scaffold](../../../../../sitecore-headless-to-xmc/assets/mock-layout-service/README.md) in reviewed plan/apply mode with the explicit stage and `--preview-stage-sha256`. It consumes approved selected captures, current mapping results and explicit examples; it is not a broad recapture or a substitute for Discovery. JSS targets require a separately verified target loader/integration; the scaffold is SitecoreAI-specific. Order remaining prerequisites as applicable: `mock-layout-scaffold` → `shared-styles-shell` → `preview-foundation` → page-aware rendering work. Omit already equivalent scaffold/style work independently, while retaining the readiness task. Before `preview-foundation`, create the pair skill's task-owned preview-input manifest from the selected fixture, exact route, explicit layout path, deployment provenance and completed prerequisite results. The task consumes that manifest instead of scanning repositories, fixtures or stale indexes. Missing route/layout evidence is one bounded recovery gap with source/site/language/route provenance and an owner. Preserve route case/suffixes, `home/index.json` root, and one language per preview tree. Do not repeat broad GraphQL queries or impose one target's mock integration on another framework.
- `shared-styles-shell` is one reviewable prerequisite task, never a hidden part of the first rendering batch. It consumes Discovery's recorded style analysis and target-baseline evidence to deliver only the approved shared foundation: root style entrypoints and import order, shared shell behavior, common style partials, shared fonts/icons/assets, and any necessary build transform or runtime dependency. It must record its owned paths, installed/retained dependencies, baseline revision and selected-route verification; it must not recrawl or rediscover the source. For the conditional Headless/JSS preparation, `preview-foundation` then consumes the manifest-backed delivered foundation plus root layout and placeholder wiring, and performs a browser-capable read-back of the one agreed fixture-backed route. It proves the route loads, the mock client/route integration is active, the delivered shared foundation is active, and intentional unresolved Sitecore renderings are visibly distinguishable. A configured app, started server, or root URL is not a ready preview. If any foundation task cannot complete safely, represent it as a clearly owned blocker; do not mark dependent rendering work successful on static checks alone. Independent work with valid independent checks may proceed only when its approved dependencies do not require this preview, and its route/browser acceptance remains pending until the foundation is repaired.
- Preserve incremental visual attestation: on an agreed route containing migrated and not-yet-migrated renderings, migrated renderings must render their real target implementations and confirmed not-yet-migrated renderings must remain visibly identifiable as Sitecore-specific orange placeholder boxes. Preserve nested placeholder children when the framework supports it. A failed route, missing fixture, compile error, or unknown mapping is not an unmigrated rendering and must not be disguised as a placeholder. Inspect the existing target SDK behavior first. If this fallback is absent, create/route a separately scoped, reviewable Sitecore preview-foundation task using the supported framework extension point; never hand-edit generated maps or protected scaffold files, and never use a visual stub to hide a failed migration.
- Do not dispatch a task as visually validated until an actual browser-capable preview has loaded its agreed route with the expected captured data and no unexplained runtime/build failures. The task evidence must identify which migrated rendering(s) were visible, which unresolved renderings showed the intentional fallback, and any nested/route limitations. If the available browser capability cannot inspect the preview, report visual validation as not run rather than inferring it from HTTP or logs.
- For MVC, inspect real head/body call sites and record head-placement hazards, resolver-pending work and unmapped helpers against the stable rendering ID. For Headless/JSS, use actual Layout Service fields and the confirmed target SDK. Follow the pair skill for detailed transforms; this profile defines phase control and acceptance, not a duplicate transform recipe.

## Work planning and execution

1. Use Discovery's approved entity-to-task mappings and `scripts/next-work.mjs --limit 50` to determine workflow/dependency, parent/frontier and route-host readiness; never rank an ineligible task as ready. For every rendering scope, do not rank any route-dependent rendering task until the workflow records current `preview-foundation` evidence; when `shared-styles-shell` is planned, do not rank `preview-foundation` until that task's evidence is current. Prioritize this chain before page-aware work. Among otherwise eligible singleton rendering tasks, use this evidence-based priority: used on an agreed route first; then rendering kind (`sublayout`, `json-rendering`, `view-rendering`, `controller-rendering`); then source complexity (`view-only`, `view-with-fields`, `controller-with-logic`); then fewer observed hazards, fewer framework signatures, and stable rendering ID. Missing classifications sort last and remain unknown—do not repeat broad discovery just to manufacture a rank. For approved grouped tasks, the group stays the scheduling unit; process its entities parent-before-child and use this ordering only among otherwise independent members. A failed, skipped, excluded or unknown parent is a decision-required gap, not permission to silently bypass it. Proceed without a rendered host only after an explicit recorded decision; verify at a page root and label that limitation.
   For the selected mapped task, create one `prepare-task-packet.mjs` handoff before dispatch. Its declared evidence references must be current, hash-bound records already retained by Discovery: the selected rendering's stable identity/source join, the applicable page-aware route/fixture record, the relevant code-analysis report and, only when applicable, resolver-candidate or target-baseline evidence. The packet points at those files; it does not copy their contents or create another source of truth. Do not inspect every discovery report, source tree or resolver record in the coordinator. If the selected rendering's required join, route/fixture or declared evidence reference is absent, stale or contradictory, return that single bounded gap rather than broadening the task or rediscovering the migration.
2. Honor the user-approved task granularity (per rendering, route/feature batch or larger deliverable). A batch does not reduce per-rendering evidence requirements: every mapped rendering needs its own successful `entity-result` artifact bound by `entityId`. A task may be marked done only when all mapped renderings meet acceptance; on partial success, keep the task failed/blocked and preserve only independently proven entity-result artifacts. Never derive task count from raw React file/component counts.
3. Give the worker each entity's stable rendering identity, source implementation/join evidence, target paths, relevant source baseline, field/data contract, parent/route/validation route, current mock fixture, prior decision and exact acceptance checks. A rendering/route task may change component-local styles and add a source-declared, non-jQuery package directly imported by an assigned implementation. It must compare current source and target manifests, pin the source or recorded compatible version, use the target repository's existing package manager, update the lockfile, run a package-manager health/type/build check, and include manifest/lockfile paths in its checkpoint and entity result. It must not add an unreferenced package, alter build configuration or root entrypoints, copy global styles/fonts/icons/assets, or modify the shared shell unless that scope explicitly owns the current task. If the source/version evidence is absent, the dependency conflicts with the target, or it needs wider configuration, return a bounded blocked result naming the missing prerequisite and source/target evidence. Missing source paths require bounded recovery, explicit user exclusion or a clearly labelled stub—not guessed completion.
4. Treat a canceled, empty or nonterminal worker return as an incomplete attempt, not a task result. Keep the task blocked, preserve the attempt's bounded evidence directory and inspect only its declared paths, current hashes and any existing checkpoint before deciding recovery. Do not mark it done, request human verification, create a checkpoint commit or dispatch another task. Resume the same task scope only after that inspection: reuse the same job when the runner can safely resume it, otherwise dispatch one fresh bounded worker with the exact task scope and the incomplete-attempt evidence. If ownership or changed-file scope is ambiguous, stop and ask for a scoped recovery decision; never hide partial changes in an automatic commit.
5. Before editing, inspect target `git status --porcelain` and `HEAD`. Preserve unrelated uncommitted work; if a task-owned path already has user changes, checkpoint only those exact paths as its baseline. After task checks pass, create a local checkpoint commit containing exactly this task's changed paths and include the full commit SHA plus changed-path scope in the task result. Follow [Git operations](../../../git-operations.md) and [checkpoint guidance](../../../checkpoints.md); a local commit is sufficient, and pushing/merging or changing branch state requires separate explicit authorization.
6. Translate through the correct pair skill: Headless/JSS to the confirmed target SDK, or MVC reconstruction to the target framework with bounded stubs replaced by working data/render behavior. Preserve field spelling, markup/class selectors, editor behavior and source interactions; classify unsupported helpers and deferred resolvers rather than inventing endpoints.
7. Validate each rendering after its changes: static/type/build checks, actual target route/browser render, and applicable structural/selector/interaction checks. For incremental Sitecore visual proof, use the route/fallback acceptance above and compare against the matching source route, site, language, content and viewport. HTTP 200 alone is not visual parity. Attach per-rendering evidence with current input provenance, explicit checks, `entityId`, changed paths and checkpoint. Keep user visual attestation separate from technical success; approval of a batch task does not attest each rendering unless the user actually reviews that evidence. After presenting the structured result/evidence, ask separately which rendering(s) the user verified, did not verify, or wants to pause; record keyed `verification` decisions against each item's exact selected result/evidence hashes. Then ask separately whether to continue, redo, skip, restore, pause, or finalize. Never merge these prompts or infer attestation from continuing. A deferred/unsigned item may remain technically done and be revisited in a later sign-off pass; user deferral is not attestation.
7. Retry a failed tool call only after diagnosing its returned error and correcting a safe invocation/input issue. For a missing source path, ask for a confirmed path, run a bounded source-path search, record an explicit skip, or use a clearly labelled stub only when the user approves that reduced outcome. For other failures, show the concrete evidence and ask whether to retry, skip, restore a named checkpoint or stop. If the user rejects an implementation result, use the tester's read-only diff-on-failure diagnosis before redo; do not dispatch that tester on every successful rendering. For system failures, unsupported behavior or unsafe mutations, stop that item with precise evidence and an actionable resolution. A scoped skip requires a current explicit decision and remains skipped—not completed.

Redo/restore preserves unrelated completed work, records the affected scope and decision, and invalidates stale downstream evidence and entity attestations tied to changed result/evidence hashes. On restore, map rolled-back checkpoint references to task/entity evidence; reopen only the tasks/entities whose outputs were actually undone, then rerun their dependent checks. Never reuse a screenshot, attestation or acceptance result after a relevant code/input change.

## Exit audit

Reconcile every included Sitecore rendering ID to exactly one approved task mapping and current entity-bound result. Run the coverage report with current task/evidence validation and decisions. The approved Code Migration workflow must contain one aggregate coverage-audit task for the tester; if it is absent, request approval to revise/synchronize the workflow instead of silently dispatching an untracked phase task. The tester independently reconciles scope, task/entity results, route coverage and evidence before phase closure. Report counts separately for technical coverage (verified, pending, running, failed, blocked, explicitly skipped, unresolved and excluded) and human attestation (attested, not verified, paused, unattested, stale or ambiguous); include missing/unmatched IDs, route/parent gaps, failed checks, stale attempts, unresolved hazards and checkpoint references. A sample or task-level `done` is not proof that all renderings in a batch passed. Do not report the phase as fully verified while any included rendering remains unsigned; if the user elects to close with gaps, record that explicit reduced-acceptance decision and list the unsigned items as unresolved rather than passed.

After the audit, mark this phase complete only if its required tasks/evidence meet the approved plan. Summarize the results and any gaps to the user. Derive any next phase(s), dependencies and task granularity from Discovery plus Code Migration findings and the user's already-approved plan; do not automatically say Content Migration is next or mutate the plan without the required approval/reconciliation.
