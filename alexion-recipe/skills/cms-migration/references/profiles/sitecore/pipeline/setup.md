# Phase 0 — Setup

This is the CMS-specific procedure inside the artifact-owned Setup phase, executed by `setup.cms` after complete source and target role configuration and shared-state synchronization. The migration-artifact skill owns phase/task creation and the final audit/handoff. This procedure establishes the remaining migration scope and applicable platform prerequisites and prepares the target application. It does not run Discovery. Read `../../../workspace-setup.md`, `../../../workflow-state.md`, `../../../../../sitecore/references/setup/setup-recording-contract.md`, `../../../../../sitecore/references/setup/capability-requirements.md`, and `../../../migration-artifact-contract.md` before acting.

## Entry invariants

- Do not guess a migration mode, site, language, repository or branch. The user must confirm each value; `kajoo` is never an implicit target branch.
- Ask Setup questions in dependency order. Batch only independent questions under the [dependent-question rules](../../../decisions-and-approvals.md). Confirm the connection before enumerating its repositories/sites; confirm the repository before fetching branches, and confirm the site before fetching its available languages and asking which to use. Confirm migration mode before asking mode-specific questions; ask Discovery-only surfaces only for Discovery-only. Confirm the destination/app and initialization action before requesting scoped mutation/push approval. Wait for each prerequisite answer and refresh the relevant candidates before the next question. Dispatch the selected-site Layout probe only after the user confirms both site and language. Reuse confirmed answers and successful probes; do not report expected input sequencing as a worker failure.
- Do not modify or reset the target Sitecore instance unless a specific Setup repair/provisioning step is selected and approved. Never wipe or reset the instance.
- Use the artifact-owned Setup phase, task IDs and workflow bindings supplied by migration-artifact. The recipe does not seed phases. Validate the existing sandbox workflow before dispatching CMS work; never create a second plan or adopt a phase by name.
- The migration artifact is the durable description; context/workflow/evidence/decisions/reports are the execution record. Follow the artifact lifecycle exactly.

## Entry bootstrap (before context creation)

1. Read `kajoo/get-workspace`, project context, the existing migration artifact and the bound Setup records. If preparation or its bindings are missing, return to migration-artifact for repair; do not create a replacement artifact or generic Setup phase.
2. Read the profile workflow asset (`assets/profiles/sitecore/workflow.json`) as a template, not an active plan. The active `${MIGRATION_STATE_FILE_DIR}/workflow.json` initially contains only Setup. Validate it and read back `currentPhase`, task counts and blockers; preserve statuses and all existing phases on resume. Repair a missing workflow through migration-artifact using the verified bound records, never by resetting tasks or activating Discovery.
3. Verify that `setup.source` and `setup.target` have current completion evidence. For both role tasks, require owner-completed task reports and current isolated role-configuration/result evidence; missing required role facts return to that same task rather than being silently deferred until this one. Reconcile only this artifact's explicitly bound Kajoo records using the workflow plan-sync contract. Read back records; do not insert duplicates. Every later task/phase status change must be synchronized and read back.
4. As the assigned CMS integration owner, verify the artifact roles already persisted by their owners against both role files, then build combined context, preserving unrelated values and reading back the adopted facts, recording its real `artifactId`, source/target connector roles, repository paths, selected refs/revisions and reference decisions. Reuse confirmed answers and successful probes. Keep the existing `content.phases` links; unrelated project epics never become migration phases implicitly.

## Ordered checkpoints

The ordered checkpoints below keep generic coordination in the CMS hub and Sitecore mechanics in the Sitecore references. The assigned `setup.cms` owner performs its checkpoint work, writes its task evidence and Setup decisions, validates/reads back combined context and artifact, then saves its final Technical report and task status. The coordinator projects that owner result into the workflow; it does not carry out integration or complete the owner’s task.

All remaining S1–S11 checkpoints belong to `setup.cms`. Generic connection/repository/reference readiness is already recorded by `setup.source` and `setup.target`; reuse it and perform only missing, stale or scope-specific work. `setup.audit` independently verifies Setup evidence. `setup.prepare-discovery` then creates the visible profile-owned Discovery plan and is the terminal fifth Setup task. The user's phase-continuation choice is a conversational boundary decision, not a project task. Do not create S1–S11 or the continuation choice as separate product/Jira tasks.

### Probe transport rule

The canonical PowerShell script is the behavioral source and its hash is provenance only. Do not add a second exact-byte acceptance gate: connector-added comment markers, whitespace, or line-ending differences are acceptable when the job is terminal, the result is non-empty/schema-valid, and the classifier succeeds. Retry only an execution-changing wrapper or invalid output.

### Artifact update rule

Each sequential source/target owner persists and verifies its assigned artifact role and matching role file before completing. This CMS task owns combined context/Setup decisions: after both owner results pass, fetch the current artifact, verify the roles already saved by their owners, preserve unrelated fields and phase/state-file links, and reuse the saved values. Missing or stale artifact role persistence returns to its owner rather than being filled here. Persist/validate/read back combined context and actual Setup choice provenance. Missing known applicable site or stack facts block this integration; contradictory inputs return to the owning role without rewriting a successful owner’s report or repeating compatible probes.

At the end of S2–S11, retrieve the artifact, merge the newly verified platform/repository/site facts, and update it. Keep `content.phases` synchronized to the included project-epic database IDs. Do not add workflow state, task IDs, mode, approvals, raw probe output or unresolved blockers to artifact content. Discovery may add or remove phase IDs only after the project plan has been reconciled.

### Deferred capability rule

Setup must distinguish a missing capability required to finish Setup from a capability that is only needed by a later phase. For example, a target SPE file-download failure may be recorded as `phase-deferred` when target content is not in the selected Setup/Discovery scope; it remains visible in `reports/setup-prerequisites.json`, the Setup summary and the later phase plan. It must never be reported as ready, but it must not block Setup when no current gate depends on it. A source capability required to select/probe the source site or initialize the requested scope remains `setup-blocking` until green or until the user explicitly changes scope so the capability is no longer required.

### Site probe failure rule

An empty bare array (`[]`), non-JSON output, or an envelope missing `sites` is a probe execution/contract failure—not a verified “no sites” result. Preserve the terminal output in evidence, correct the script invocation, and retry within the bounded probe budget. Only a valid envelope with `sites: []` may be reported as “no candidates”; that remains a blocking Setup finding requiring user-provided site path or remediation.

## Completion and exit

The `setup.audit` owner persists and reads back `reports/setup-summary.md`, `reports/setup-completion-assertion.json` and `reports/phase-boundary-setup.json` on every termination path (success, blocked, canceled or user stop). The summary must list verified, pending, blocked, deferred and unresolved items, evidence paths and the exact next-phase scope. Mark `setup.audit` complete only when context is valid+complete, the prerequisite evaluator is complete, required terminal evidence exists and applicable initialization succeeded or is explicitly inapplicable. Completing `setup.audit` completes evidence verification only. The orchestrator then runs `setup.prepare-discovery` to create and verify the visible plan before Setup completes; no task remains in progress while awaiting the user's execution choice. Return to migration-artifact's completion/handoff procedure. Discovery planning creates and links the phase and tasks after the audit, without starting them. Todo tasks are defined; draft tasks explicitly identify missing task-specific inputs. Its entry procedure requires explicit continuation before any execution. Never offer that choice while any Setup blocker remains.
