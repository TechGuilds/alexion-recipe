# Final target website verification

Use this procedure after the independently audited presentation application. The tester collects evidence and runs the gate; the coordinator obtains the human page decisions and owns the separate final phase-continuation decision. Technical consistency and a passing functional test do not establish visual parity.

Run locally with a fresh output directory:

```text
node scripts/verify-target-website.mjs --input website-verification-input.json --output website-verification-attempt-01
```

The command creates `website-verification-report.json`. It does not publish, write to Sitecore, authorize a mutation, or advance workflow. `ready` means the supplied evidence meets this explicit page scope and coverage requirement. Review `untestedPageIds` and `limitations` before requesting final continuation; an untested page has no website verification claim.

## Capture the actual applied target

`contracts/website.schema.json` is the strict public contract. The `websiteVerificationInput` contains `version: 1`, `scopeId`, the tester's exact `taskId`, SHA-256 artifact references for `applicationAuditInput` and `targetCapture`, `minimumPages`, nonempty `requiredChecks`, `browserEvidence`, and `decisions`. Artifact paths are relative to their containing manifest; human decision input paths are relative to the operation input, consistent with preview review. Paths must stay inside that artifact directory. Use immutable attempt artifacts so the audit and page decisions remain reproducible.

For applications with several approved language/version contexts, add `additionalContextInputs` to the root input: an array of artifact references to complete website verification inputs for the other contexts. Each child must use the same resolved current application audit, plan, task and scope, and preserve the agreed minimum and required functional checks. Children cannot contain `additionalContextInputs`. Root plus children must cover exactly the approved original application review manifest set, with no duplicate or unrelated contexts. An omitted language/version blocks readiness even when the root context passes. The report's `contexts` records each target tuple, preview/capture hashes, page results, and rendering coverage; `untestedContexts` lists omitted contexts. The top-level page arrays merge page IDs, so use the context records to distinguish translations of the same Sitecore item.

The gate replays `auditPresentationApplication` into an isolated temporary directory and checks the successful immutable receipt/download history and independent target state. No submitted `ready` flag substitutes for this replay. The website capture must follow the audit's independent target observation (`applicationAuditInput.targetState.capturedAt`), remain within its declared expiry window, and bind the exact application plan SHA-256 and original approved preview manifest SHA-256. Replaying an audit later verifies the original observation; it does not silently move its timestamp forward.

A `targetWebsiteCapture` has kind `target-website-capture`, version, scope, full `target`, `capturedAt`, `expiresAt`, `applicationPlanSha256`, `previewManifestSha256`, `sourceBaseline`, and `pages`. Copy the exact preview target tuple: instance, database, capture state ID, site, language, item version, and device. Each page identifies its mapped `pageId`, `route`, actual target website `url`, raw Layout Service `layout` reference, and `transport` reference. Capture at least the agreed number of pages and every required rendering/variant combination. The gate also preserves the approved preview minimum; reducing scope requires a revised approved workflow, not a smaller verifier input.

Each `targetWebsiteTransport` is a collector's immutable response record with kind `target-layout-service-response`, version, target tuple, response timestamp, `requestUrl`, `websiteOrigin`, status 200, response `bodySha256`, and both plan/manifest hashes. The read request must use the actual target Layout Service endpoint `/sitecore/api/layout/render[/<configuration>]` with explicit `sc_site`, `sc_lang`, `sc_database`, `sc_itemversion`, `sc_device`, and route `item` query values. `websiteOrigin` binds the rendered website separately from a CM Layout Service host. Preserve the actual raw response bytes as the layout artifact. A deployment that does not support this explicit read context needs a separately verified capture adapter before using this gate; do not invent successful requests.

The verifier compares the captured route identity, material fields, layout association, rendering UIDs and component names, datasource references, parameters, placeholder ancestry and ordering with the original canonical preview. The independent audit separately verifies physical rendering definitions and design associations. Actual target payloads may match the approved preview exactly; byte equality establishes neither provenance nor a problem. Virtual manifest kinds, mock artifact paths, and localhost/mock/preview URLs are rejected. Evidence must come from trusted target and browser capture mechanisms; local manifests and hashes preserve evidence integrity, but do not authenticate an arbitrary collector's assertions. Do not fabricate live provenance or add metadata to a preview file to impersonate a target response.

This comparison supports contexts whose captured effective Layout Service semantics match the canonical composition. An SXA deployment may transform physical placeholder paths or signature parameters while expanding partial designs. If those transformations prevent a direct semantic comparison, obtain an explicitly verified normalization adapter and its evidence before final verification. This command does not guess path rewrites, strip signature parameters, or claim compatibility for an untested expansion mechanism.

## Approve the source baseline and compare each page

`sourceWebsiteBaseline` has kind `approved-source-website-baseline`, version, scope, `sourceInstanceId`, `approval`, and pages containing the mapped `sourcePageId`, route, source URL, and PNG/JPEG screenshot reference. The baseline approval is a standard human `verification` decision with choice `verified`, exact website task and scope, actual `userResponse`, timestamp before the target capture, and exactly the current source screenshot references in its inputs. Retain the source page mapping; a screenshot from another source page cannot cover the mapped target page.

For each tested target page, collect `targetWebsiteBrowserEvidence` with kind `target-website-browser-evidence`, version, exact scope/task/target, timestamp at or after the target capture, application/preview/capture hashes, page ID, route, actual target URL, a screenshot, named functional checks, errors, comparison, and navigation observations. Screenshots must be hash-verified PNG/JPEG bytes; renaming a text file is insufficient. Browser errors or any failing named check block acceptance. Every required functional check must appear by its exact agreed name, such as `primary navigation`, `main CTA`, or `form submission validation`.

`comparison` contains references to the exact approved source screenshot and this page's actual target screenshot, `passed`, and meaningful comparison `notes`. Record layout, typography, content, imagery, responsive behavior, and any accepted differences in the comparison notes. `navigation` contains actual target `fromUrl`, `toUrl`, and `passed` observations; the observations must involve this target page. Preview links and off-target hosts do not count. A technical comparison result is supporting evidence only.

The coordinator obtains one standard human verification decision per tested page. Its `entityId` must be the exact target page ID, task and scope must match this website verification input, and the timestamp must follow the browser capture. Record the user's real response; the agent must not supply one. The decision must bind exactly four current artifacts: this `applicationAuditInput`, `targetCapture`, the page's browser evidence, and the source baseline. A `not-verified` or `pause` response blocks readiness. Missing decisions leave pages untested and cannot count towards either the minimum pages or required rendering coverage.

Once the website report is ready, pass its exact current evidence to the coordinator for the separate `verification.approve` operation. Human page confirmation does not itself grant final continuation. If the live target, source baseline, browser capture, required functionality, or user response is unavailable, preserve the blocked result and describe the missing checks accurately.
