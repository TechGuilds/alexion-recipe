# Apply approved target presentation

Use this procedure only for an assigned application task after successful human preview review. It implements the standard SXA Partial Design and Page Design model through verified SPE capabilities. It does not convert a site, create component code, move content or publish. Original source XML is never copied to target presentation fields.

## Required evidence

The runtime authority is [definitions.schema.json](../contracts/definitions.schema.json). The TypeScript interfaces document the handoffs. All artifact references are paths and SHA-256 hashes of actual bytes, relative to the selecting request unless stated otherwise. Keep original inputs immutable; write each new attempt into a fresh directory.

`applicationInput` selects `scopeId`, `taskId`, one or more successful `reviewInputs`, an `applicationProfile`, verified `applicationCapabilities`, optional `targetState` and `maxOperationsPerBatch` (1–20). Each review remains one explicit language/version/device context. Combined reviews must target the same site and device. Shared design composition must agree across contexts. The target-data handoff must also contain `rawFields` with the original Sitecore string value, field ID and name for every preview field. A structured JSS field projection alone cannot prove that the underlying value is unchanged.

The profile identifies the exact target instance, authoring database, selected connector, site root and marker ID/template/path; source roots; existing Partial Designs and Page Designs folders; existing design templates; the verified Partial Design layout; optional Page Design `Layout` field adapter; physical nested placeholder bindings; and inspection evidence. Standard folders are `<site>/Presentation/Partial Designs` and `<site>/Presentation/Page Designs`. Design templates must be, or inherit, the SXA Partial Design and Page Design templates. Custom storage/field types or different SXA conventions require a verified adapter before use. The optional Page Design Layout field requires an existing reference field; page layouts are always explicitly selected.

Nested placeholder bindings select the virtual owner (`partial:<key>` or `page:<normalized-target-guid>`), occurrence UID and actual target placeholder path. Determine that path from the target component conventions and include it in profile evidence. Logical child keys do not establish dynamic placeholder paths.

Capabilities bind the same instance/database/connector and a current verification window to evidence. Confirm read consistency, file export/download, request/capture/backup/journal limits, command availability, authoring database, full-item backup and tested restore, exclusive writer coordination, durable journal continuity and actual layout round-trip behavior on this platform. Boolean flags record verified capabilities; setting them does not perform the verification. Missing capabilities block application. Test the selected SPE/Sitecore deployment with a bounded pilot before the full migration.

## Dry-run and approval

1. Run `plan-presentation-application.mjs`. Without `targetState`, it emits `presentation-read-request.json` and its connector envelope. Run that exact envelope through the selected connector, download the exported `presentation-state.json`, and bind its actual hash as `targetState` in a new application input.
2. Rerun the planner. It replays the composition and human preview reviews, verifies the target material values and definitions, and classifies deterministic design creation, exact reuse, page updates and template associations. Conflicts produce no executable batches. Existing designs with mismatched content cannot be overwritten or implicitly adopted. Explicit reuse must exactly match; unrelated template mappings remain present.
3. Inspect every change and exclusion. Page Designs reference Partial Designs; components belong to Partial Designs or selected pages. The writer replaces only the selected device's approved effective page rendering list and associates the approved design. Redundant page instances are removed only when the reviewed composition supplies the desired result. Other device XML and unrelated observed fields are preserved.
4. Initialize a dedicated journal with `record-presentation-execution.mjs` using `presentationEvent` action `initialize`, explicit scope, target and a new `journalDirectory`. Paths are relative to the selecting request; an absolute journal path is recommended. Keep the complete directory throughout recovery/resume.
5. For each dependency-ordered batch, obtain a fresh capture using the original read request. `presentationWriteInput` selects the original application input and canonical application plan, batch ID, fresh `currentState` and journal directory. Run `prepare-presentation-write.mjs` without approval to produce `presentation-execution-review.json`.
6. Present that exact review to the user and record the existing CMS `mutation` decision with matching scope/task, actual user response and the review path/hash in `inputs`. Add its reference and the exact prior `review` reference to a new write request. Preparation checks drift, dependencies and capabilities, reserves the immutable journal, then emits the connector request. Preview approval never authorizes this mutation.

Page-specific Page Design fields may be versioned, unversioned or shared. Shared/unversioned writes require every affected page context to be covered by compatible approved reviews. Template association also requires a bounded complete scan of consumers within the site. Missing coverage blocks the batch. An inherited Page Design that overrides template selection requires an explicit page-specific choice. Association changes affecting other devices require separately supported reviewed handling; do not assume one device's preview approves all devices.

## Execute, reconcile and resume

Dispatch each reserved envelope exactly once on the selected connector. Record action `submitted` with the actual connector/job ID, request ID and current `expectedHeadSha256`. Poll that actual job; a timeout is not failure or success. Record `unknown` when outcome is uncertain and reconcile the same job. Never generate another request, remove a local/server lock or repeat a potentially applied batch to escape uncertainty. A reservation that has not been dispatched also requires explicit reconciliation; resetting the journal discards the safety boundary.

The writer checks actual target identity, templates and before-state; serializes affected existing items before the first mutation; then creates or updates in dependency order. It journals intent before each operation and reads back actual layout/occurrence/field values afterward. New designs receive deterministic IDs and reviewed language versions. Page content and versions must already exist. Failed operations retain actual partial observations, later operations are skipped, and no automatic rollback occurs. Failed or incomplete backups prevent mutation. Server request claims prevent applying the same request twice; an interrupted server lock remains for operator reconciliation.

Consume the selected connector's terminal `kajoo-export` transfer containing the receipt and every exported backup/journal file. Preserve each remote relative path as the suffix of its local transferred path. The read collector uses the same terminal export convention for `presentation-state.json`. If terminal transfer is absent or partial, retain the actual job ID and transport error and reconcile that job; do not invent a per-file download tool or assemble a substitute export. Record a `terminal` event with the exact review, receipt, bound job ID and `backups` references covering all transferred backup **and journal** files. The recorder verifies their hashes, sizes, identities and actual logical postconditions before clearing the active reservation. A failed terminal receipt remains failed history and cannot be blindly rerun. Recover using the transferred full-item serialization and the platform's previously verified restore procedure, inspect current state, then create a new reviewed plan. Do not edit a checkpoint, forge a terminal receipt or force a retry.

Preparation resumes a successful batch as a no-op only after fresh target verification; later batches require successful predecessors. Preserve the original canonical plan when resuming. The application journal is independent of workflow status and of the content identity map.

## Independent verification

After all batches, run the original read request again. Use `applicationAuditInput` with the original application input/plan, journal directory and a new `targetState` captured after terminal reconciliation. `audit-presentation-application.mjs` verifies each changed or reused item against the plan and checks completed history. Obtain user confirmation. Then perform final target-site visual and functional checks through the assigned verification task. A technical presentation audit does not establish website parity, publish content or advance workflow state.
