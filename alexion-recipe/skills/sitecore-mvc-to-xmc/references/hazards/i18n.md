# Sitecore MVC Helper — i18n / Globalization

Classifies and translates Sitecore globalization helpers (`@Translate.Text`, `@Translate.TextByLanguage`, `@Sitecore.Globalization.Translate.*`) to the SitecoreAI Content SDK dictionary surface via next-intl. Loaded on demand by the `sitecore-mvc-to-xmc` hazard-gate whenever `mvc.viewSignals.translateHelperCalls` is non-empty for the rendering being converted.

Use this skill when a `.cshtml` calls `@Translate.Text(...)`, `@Sitecore.Globalization.Translate.Text(...)`, or `@Sitecore.Globalization.Translate.TextByLanguage(...)`.

## Match keys (from hazard inventory)

- `Sitecore.Globalization.Translate.Text(string)` — verdict `available-OOTB`.
- `Sitecore.Globalization.Translate.TextByLanguage(string, Sitecore.Globalization.Language)` — verdict `partial-OOTB`.

## The single bridge — how a translated phrase resolves

There is exactly **one** path from a dictionary key to a rendered phrase. Do not bypass it:

```
src/i18n/request.ts (getRequestConfig)
  → client.getDictionary({ site: page.siteName, locale: page.locale })
  → messages[page.siteName] = <the flat { key: phrase } map>
  → next-intl
  → useTranslations(page.siteName) / getTranslations(page.siteName) in the component
```

`request.ts` namespaces the dictionary **by site** (`messages[page.siteName] = dict`). The dictionary JSON itself is keyed by dictionary key only — never site-prefixed inside the file. Therefore the component **must** pass the site as the next-intl namespace: `useTranslations(page.siteName)`. A bare `useTranslations()` looks up at the catalog root, finds nothing, and renders the raw key — that is the bug this skill exists to prevent.

In local/mock mode the dictionary is served from disk: `fetch-and-deploy-mvc-mock-dictionary` deploys `public/mock-dictionary/<site>/<locale>.json` (a flat `{ key: phrase }` map), and the mock client's `getDictionary` reads it. Source phrases come from the **site's dictionary domain** in the content tree (resolved from the site definition's `dictionaryDomain` attribute, typically `/sitecore/content/<site>/Settings/Dictionary`) — **not** `/sitecore/system/Dictionary`, which holds only third-party/module strings.

## Translation rules

There are three official Content SDK access patterns, all namespaced by `page.siteName`. Pick the one that matches the component kind.

### `Translate.Text(key)` — non-async server component

```razor
<h2>@Translate.Text("Heading.Welcome")</h2>
```

```tsx
import { useTranslations } from 'next-intl';

export function Heading({ page }: { page: Page }) {
  const t = useTranslations(page.siteName);
  return <h2>{t('Heading.Welcome')}</h2>;
}
```

### `Translate.Text(key)` — async server component

```tsx
import { getTranslations } from 'next-intl/server';

export async function Heading({ page }: { page: Page }) {
  const t = await getTranslations(page.siteName);
  return <h2>{t('Heading.Welcome')}</h2>;
}
```

### `Translate.Text(key)` — client component

The generated catch-all `Page.tsx` wraps the tree in `NextIntlClientProvider`, so a `'use client'` component reads translations with the same hook, still namespaced by site:

```tsx
'use client';
import { useTranslations } from 'next-intl';

export function SeeMoreButton({ page }: { page: Page }) {
  const t = useTranslations(page.siteName);
  return <button>{t('Search/See More')}</button>;
}
```

### `Translate.TextByLanguage(key, language)`

- If the `language` argument is the context language (`Sitecore.Context.Language`), translate as `Translate.Text(key)` using the access pattern above for the component kind.
- Otherwise, emit `hazard-pending: i18n — TextByLanguage("<key>", <language>); explicit-language dictionary access not first-class in Content SDK v1`.

## Anti-patterns

- Do NOT inline string literals to bypass the dictionary surface.
- Do NOT import a `t()` helper from `lib/i18n` or call `@sitecore-content-sdk/core/i18n` directly — **no such helper ships, and a hand-rolled one bypasses the single bridge** (`request.ts` → `getDictionary` → `messages[page.siteName]`). Always read through next-intl's `useTranslations(page.siteName)` / `getTranslations(page.siteName)`.
- Do NOT call `useTranslations()` / `getTranslations()` **without** the `page.siteName` argument. The catalog is namespaced by site; the bare call resolves nothing and renders the raw key.

## Validation — assert the phrase, not the key

A translation that renders the **key** is a silent failure. Validation must assert the resolved **phrase**, not merely that the key string is present (the old check passed green for every i18n-hazard component while every one of them rendered raw keys).

- For every key the mock dictionary actually backs, assert the **phrase** renders. Example: a See More button bound to `Search/See More` must render **"View More"** (the real source dictionary value) — never the literal `Search/See More`.
- Keys the source dictionary does not back are **omitted** from the mock (the runtime miss-path renders the raw key). They are out of scope: do not assert a phrase for them and do not record them as a tracked gap.

## Gate-3 ledger

Every `@Translate.*` invocation must either appear as a next-intl read (`t('...')` via `useTranslations(page.siteName)` / `getTranslations(page.siteName)`) in the generated TSX, or be recorded as `hazard-pending: i18n — ...`.
